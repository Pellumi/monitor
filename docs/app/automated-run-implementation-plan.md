## Context

Tellann today is human-driven: `BrowserObserver` (packages/browser-observer) launches Playwright Chromium and only *observes*. It never calls `click`/`fill`/`getByRole`. GUIDED/ASSISTED/OBSERVATION_ONLY all need a person at the keyboard. The pasted design proposes **Automated Run**: execute one pinned, published Flow version from its initial state to one user-selected terminal state, using the codebase model and a managed browser, capturing evidence at every state. It is a **deterministic execution engine**, not an AI clicking screenshots. Intent stays human-owned (declared Flow); Tellann only works out *how* to realise transitions.

Scope decision (user): the **full 10-step roadmap**, delivered as waves. Step source decision (user): **derive from code + instrumentation**, no manual step authoring on Flow transitions.

### Non-negotiable invariants
1. Automated Run is **never** allowed in PRODUCTION (server 403 + desktop refusal; `productionRunModeAllowed` stays OBSERVATION_ONLY-only; reuse `assertEnvironmentActionAllowed`).
2. Run pins `flowVersionId`, initial state, target terminal state, code snapshot id, instrumentation manifest version, execution profile, persona, environment; a report months later shows exactly what was attempted.
3. Hot path (decide next action) is fully local and synchronous with the browser. Cold path (coverage, reconciliation, endpoint analysis, report) stays on the existing pipeline. No cloud call per action.
4. No LLM in the execution loop or in report text. Optional local ambiguity resolver only proposes; deterministic controller verifies. Works with model provider disabled.
5. Executor records *what happened*; **Reconciliation decides what it means** (no "missing Flow" verdicts in the planner).
6. No `networkidle`, no fixed sleeps. Stability = state predicate + critical elements + relevant requests settled + DOM quiet window + SDK signal.
7. Mutating actions are not blindly retried.
8. Source stays local; only hashes/summaries of the contract/nav graph go to the cloud.

Extend `CodeEntityTypeSchema`/`CodeRelationshipTypeSchema` (desktop-contracts 293/300). Vue/Svelte/Angular remain `UNSUPPORTED` coverage (already flagged as gap).
- `NavigationGraph` assembled from these; each edge keeps {sourceFile,symbol,route,component,trigger,confidence,snapshotId}. **Flow Slice** = subgraph reachable around the flow's checkpoints (via `projectAnalysis`/`blastRadiusInAnalysis`) so runs don't touch the full graph.
- Weighted Dijkstra/A* in `automation-engine`; cost = action count + uncertainty + mutation risk + navigation complexity; read-only high-confidence edges preferred. Pre-boundary steps are `PRE_BOUNDARY` evidence (existing scope machinery), excluded from coverage.
- **Entry Recipe cache** (local): keyed by repo snapshot + lockfile/config hash + persona + flow version; optional reuse of authenticated storage state; never skipped when login is the Flow under test.
- Fallback when framework unsupported: recipe recorded from a prior Guided run.
- `INITIAL_STATE_UNREACHABLE` / `TERMINAL_STATE_UNREACHABLE` stop reasons.

### Wave 6 - Adaptive replanning (step 6)
- After each action re-recognize actual state; on mismatch re-plan over graph + live semantic snapshot within `maxReplans`; low-confidence never keeps clicking; loop detection stops with `LOOP_DETECTED`. Emit `AUTOMATION_REPLAN` with reasons. Live-DOM candidate discovery as fallback when static graph is stale.

### Wave 7 - State-by-state evidence and report (step 7)
- Adaptive capture tiers: normal = route, semantic DOM summary, SDK events, network metadata, console errors, timings, fingerprint; anomaly = screenshot, full DOM snapshot, detailed network, trace, code-evidence expansion (gate existing `captureStateArtifacts`).
- Every action event carries: why selected, supporting evidence, expected vs observed state, confidence (auditable replay).
- `StateRunRecord[]` in evidence summary; report workers (`services/background-workers/src/qa-*.ts`, report-engine `/qa-runs/:runId/report`) gain an Automated section: pinned Flow/version, target terminal, outcome, pre-boundary vs in-flow, per-state URL/actions/timings/errors, reconciliation counts. **Also implement QRS-RUN-003 mode field.** No composite score, no model-generated text (qrs.txt ~1051).
- Cold path parallelism: after browser closes and evidence flushes, session/endpoint/browser-findings/performance/reconciliation/coverage run in parallel, then merge.
- Reconciliation (fdrs-api `reconciliation.ts`) extended with deterministic classifications for execution-derived gaps: AUTHORIZATION_MISMATCH, DATA_PRECONDITION_FAILURE, IMPLEMENTATION_MISMATCH, DECLARATION_MISMATCH (code-guard evidence, e.g. ADMIN-gated button vs TEACHER persona).
- Dashboard + desktop report views; dashboard `qa-run-handoff.ts`.

### Wave 8 - Conditional deep diagnostics (step 8)
- Playwright tracing chunks started per state, retained only on anomaly/failure (existing `PLAYWRIGHT_TRACE` artifact type); local code-evidence expansion for failed transitions; component render timing only via optional targeted instrumentation (`performance.mark/measure`, React Profiler on Flow-relevant components) - never blanket instrumentation.

### Wave 9 - Optional local semantic resolver (step 9)
- `AmbiguityResolver` interface with no-op default; verifier requires destination state + code mapping agreement before accepting a suggestion. Local runtime evaluation is a gated spike; nothing ships depending on it. Enforce no network/no source egress.

### Wave 10 - Multi-path groundwork (step 10)
- Contract and `automation` config shaped for multiple targets (`targetTerminalStateKeys[]` compatible); design + spike for branch/negative-path coverage. Not shipped as behaviour in this plan.

## Open items (resolved)
1. **Plan tier for `AUTOMATED_QA_RUNS`.** Business + Enterprise, as defaulted; asserted in `plans.test.ts` and in the acceptance script.
2. **MVP-scope wording.** Carve-out, not post-MVP: `mvp_scope.txt` restates "Autonomous Testing" as excluding test generation, validation and regression suites and carves out executing one human-declared Flow to one selected terminal state against a non-production environment. It says the feature must not grow into branch exploration without a scope change, which is why `automated-run-multi-path-design.md` treats raising `AUTOMATION_MAX_TARGETS` as needing that scope change first.
3. **`completionReason` and marker reconciliation.** `completionReason` is a plain string (stop reasons need no migration). Markers: the boundary evaluator collapses every name a state answers to (`behaviorKey`, `stateName`, `name`, `id`, `stateId`) onto one canonical key, and reads the state from `stateKey`, `toStateKey`, `state`, `stateId` in that order. Three marker shapes exist: the SDK's typed calls (`flowVersionId` + `stateKey`), hand-written slugs (`flow` + `state`) and the instrumentation adapter's (`stateId`, `checkpointId`, `source: 'tellann-adapter'`, and **no** flow version or slug). Two consequences, both fixed: (a) the executor's recogniser compares the SDK signal as text, so an adapter marker naming a state by id would never match the contract's key — `SdkSignalBuffer` now applies the evaluator's alias rule, and `ExecutableContract.stateAliases` carries the aliases (verified in real Chromium for all three shapes); (b) reading `desktop-routes.ts` (`/boundary-events` requires `flowVersionId` or `flow`) and the desktop's `handleRelayedEvents`, an adapter marker was sent with neither and would have been refused as `FLOW_EVENT_CONTEXT_REQUIRED` before the boundary ever opened — `flow-boundary-input.ts` now supplies the run's one pinned Flow version to a marker that says it came from the adapter and names no other Flow, and leaves every other marker exactly as written. **(b) was found by reading the code and is unit-tested, but has not been exercised against a live gateway**; confirm it in the platform tier of the acceptance script once run against a disposable database.
4. **Playwright aria-snapshot API.** Deviation from the plan's assumption: Playwright 1.62's `ariaSnapshot` is used only for the existing final-state artifact. The semantic snapshot the engine reads is a custom extractor (`automation-driver.ts`), because the engine needs stable element refs, hrefs, field names and enabled/visible state, which the aria text does not carry, and needs to re-find an element after a re-render.
