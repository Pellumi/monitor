Product Requirements Document (PRD)
1. Product Overview
Product Vision
Software should be capable of explaining its own quality.
The Self-Observing Testing System (TELLANN) is a software quality intelligence platform that continuously observes how applications behave, learns expected workflows, identifies deviations, and provides actionable insights into product health.
Rather than relying solely on manually written test cases, predefined monitoring rules, or user-reported bugs, TELLANN seeks to create a living understanding of how software is actually used and how that behavior evolves over time.
The long-term vision is a future in which software systems can continuously observe themselves, understand when something is wrong, explain why it happened, and assist engineering teams in maintaining reliability at scale.
2. Vision Statement
To become the intelligence layer that enables software applications to understand, evaluate, and communicate their own operational quality.
3. Mission Statement
Help software teams discover, understand, and resolve quality issues before they impact users by transforming application behavior into continuously evolving quality intelligence.
4. Product Philosophy
Traditional quality assurance focuses on creating tests.
Traditional monitoring focuses on detecting failures.
Traditional analytics focuses on measuring usage.
TELLANN sits at the intersection of all three disciplines.
The platform is built around a core belief:
Applications generate enough behavioral data to reveal their own quality state.
If user behavior, workflow completion, failures, and system responses are continuously observed and analyzed, software can develop a dynamic understanding of what "normal" behavior looks like and identify when that behavior changes.
5. Problem Space
Modern software development has become increasingly complex.
Applications evolve rapidly, release cycles are shorter, user expectations are higher, and engineering teams are expected to maintain quality across growing systems.
Despite advances in testing and observability, several critical problems remain unresolved.
Problem 1: Quality Issues Are Often Discovered Too Late
Many defects are not discovered until:
* Users encounter them
* Customer support tickets are raised
* Revenue-impacting workflows fail
* Production incidents occur
By the time issues are discovered, users have already been affected.
Desired Outcome
Teams should know about workflow degradation and quality risks before customers do.
Problem 2: Manual Testing Does Not Scale
As applications grow:
* More test cases are required
* Existing tests become difficult to maintain
* Regression testing becomes increasingly expensive
* QA teams spend significant time repeating routine checks
Testing effort grows alongside application complexity.
Desired Outcome
Quality assurance should become increasingly automated as applications evolve.
Problem 3: Existing Monitoring Tools Lack Context
Most monitoring platforms answer questions such as:
* Is the server healthy?
* Did an exception occur?
* Is performance degrading?
However, they rarely answer:
* Which user workflow failed?
* How many users were affected?
* What business process was interrupted?
* What changed compared to previous behavior?
Desired Outcome
Quality monitoring should understand business workflows, not just technical events.
Problem 4: Teams Lack Visibility Into Real User Behavior
Organizations often make quality decisions using assumptions about how users interact with software.
In reality:
* User behavior changes over time
* Unexpected workflows emerge
* New friction points appear
* Hidden failure paths develop
Without behavioral visibility, many quality risks remain invisible.
Desired Outcome
Software teams should understand how users actually interact with their applications.
Problem 5: Reproducing Bugs Is Expensive
When defects are reported:
* Reproduction steps are often incomplete
* Root causes are difficult to identify
* Engineering teams spend substantial time investigating
This slows issue resolution and increases operational costs.
Desired Outcome
Every significant issue should include sufficient context for rapid investigation and resolution.
6. Proposed Solution
TELLANN introduces a new category of software quality intelligence.
The platform holds two models of an application side by side.
The Declared Intent Graph is what a team says the application should do. It is authored by a human during onboarding, before any telemetry exists.
The Observed Behavior Graph is what the platform has actually seen the application do. It is derived from recorded evidence.
Neither is trusted over the other. The gap between them, in both directions, is the product.

Instead of relying solely on predefined rules, TELLANN develops an understanding of application workflows and monitors their health over time.
The platform enables teams to:
* State what their software is supposed to do

* Understand how software is actually used
* Discover important workflows automatically
* Detect workflow degradation
* Identify abnormal behavior
* Analyze user journeys

* Understand quality trends over time
TELLANN serves as a continuously learning quality observer embedded within software systems.

9. User Flows
User Flow A: Initial Adoption (Phase 1)
1. Organization adopts TELLANN and creates an application.
2. Team declares the flows the application is intended to support.
3. Team installs the Tellann desktop agent and binds the local codebase.
4. Desktop agent analyzes the codebase and proposes an instrumentation plan.
5. Team reviews and approves the plan; instrumentation is applied to the working tree.
6. Team runs a guided demonstration through the managed browser session.
7. TELLANN builds the Observed Behavior Graph from that run.
8. Declared intent is reconciled against observed behavior.
9. Coverage, missing states, missing flows and reconciliation results become available.
User Flow A2: Returning Use
1. Application changes.
2. Team reopens the desktop agent and runs another demonstration.
3. Reconciliation re-runs incrementally.
4. Graph drift shows what changed since the previous run.
5. Declared flows are edited where intent itself has changed.

User Flow B: Workflow Failure Detection (Phase 2)
1. Users interact with an application.
2. A workflow begins behaving unexpectedly.
3. TELLANN detects deviation from established behavior.
4. Quality insight is generated.
5. Engineering teams are notified.
6. Investigation begins.
7. Issue is resolved.
User Flow C: Quality Investigation (Phase 2)
1. Team identifies an issue.
2. Team opens TELLANN dashboard.
3. Relevant workflow is selected.
4. User behavior surrounding the issue is reviewed.
5. Root causes are investigated.
6. Resolution is implemented.
7. Workflow health returns to normal.
User Flow D: Release Validation (Phase 3)
1. New release is deployed.
2. TELLANN monitors post-release behavior.
3. Workflow health is evaluated.
4. Deviations are identified.
5. Teams assess release quality.
6. Decisions are made using observed evidence.

12. Product Roadmap
TELLANN is delivered in three phases. Each phase builds on the behavioral evidence the previous phase makes available, and none requires the previous one to be redesigned.
Phase 1 — Behavioral QA & Intent Platform
Focus
Behavioral QA, intent definition, and demonstration analysis.
A team declares the flows their application is intended to support, demonstrates the application once through the Tellann desktop agent, and receives a reconciliation of what they said against what the platform observed.
Capabilities
* Flow declaration and the Declared Intent Graph
* Desktop-driven guided demonstration runs
* Behavioral graph generation from observed evidence
* Workflow discovery
* Coverage analysis
* Missing state and missing flow detection
* Endpoint intelligence
* Session replay
* Reconciliation reporting
* QA report generation and export
Structural groundwork
Phase 1 ships a deliberately small amount of structure belonging to later phases, so customers can see the direction of travel and the architecture can be validated early:
* Graph drift across behavioral graph versions
* Bounded assisted intelligence for flow drafting and suggestion
* Anonymized cross-tenant structural pattern matching
* Recommendation evidence capture
These are supporting capability, not the Phase 1 proposition.
Outcome
Quality gaps become visible before production, from a single demonstration.
Phase 2 — Production Monitoring, Feedback & Analysis
Focus
Understanding the customer's system while it is running and real users are using it, then converting that understanding into guidance.
Phase 1 establishes what an application is supposed to do and what it was seen doing under demonstration. Phase 2 connects that model to production reality.
Capabilities
* Continuous production monitoring
* Real user behavioral ingestion
* Workflow health monitoring and degradation detection
* User journey intelligence — common journeys, abandonment, friction, bottlenecks
* Endpoint intelligence extended to production volume
* Database intelligence
* Error correlation and investigation packages
* Production-versus-demonstration comparison
* Drift of production behavior against declared intent
Feedback And Analysis
The distinguishing output of Phase 2 is not a dashboard. It is guidance.

Phase 3 — Autonomous Behavioral Intelligence
Focus
Complete behavioral understanding of a running system, and action taken on that understanding.
This is the final phase of this roadmap.
By Phase 3 the platform holds:
* Declared intent for every application
* Demonstrated behavior
* Continuous production behavior
* Historical behavior across releases
* Anonymized structural patterns across the whole network of systems on the platform
Capabilities
Real-Time Remediation
The platform detects a failure as an end user encounters it, and applies a fix to the customer's system in real time, under the customer's configured authority and with full audit.

Implementation Guidance
* Implementation suggestions
* Feature modification proposals
* Update recommendations

14. Phase Boundaries
The boundaries between phases are defined by the evidence each requires, not by ambition.
Phase 1 requires only a demonstration.
Phase 2 requires production traffic.
Phase 3 requires continuous production traffic, release history, and network-scale pattern data.
A capability shall not be moved earlier than the phase whose evidence it depends on. A capability that would produce an unreliable result on thin evidence is deferred, not shipped in a weakened form.
15. Position On Artificial Intelligence
TELLANN uses language models as an assistant to human intent declaration. It does not use them to produce quality judgements.
Throughout every phase:
* Behavioral graphs, coverage, reconciliation, findings and endpoint analysis are computed deterministically from recorded evidence and are reproducible from that evidence.
* Model output is always a proposal, and always requires explicit human acceptance before it affects anything.
* The deterministic rule library is consulted first; a model is consulted only where it returns no usable result.
* Disabling the model provider degrades the quality of assistance. It does not stop the product working.
This position is what separates TELLANN from a generative tool that guesses about software it has not observed. The product is behavioral evidence. Assistance is how that evidence becomes cheaper to describe.
