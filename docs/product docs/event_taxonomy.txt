EVENT TAXONOMY DOCUMENT (ETD)
1. Purpose
This document defines the official event taxonomy for TELLANN.
The objectives are:
* Standardize all event definitions
* Ensure consistency across SDKs
* Enable reliable behavioral modeling
* Support workflow generation
* Support analytics processing
* Support quality intelligence generation
* Enable future autonomous validation
This document is the authoritative source for all event naming and event structures.
2. Event Taxonomy Principles
ETP-001 Event-First Architecture
Every platform capability shall originate from events.
Supports architecture principles.
ETP-002 Immutable Events
Events shall never be modified after ingestion.
Derived data must be created separately.
Supports DFD principles.
ETP-003 Consistent Naming
All event names shall use:
UPPER_SNAKE_CASE


Examples:
PAGE_VIEW


BUTTON_CLICK


API_REQUEST


API_RESPONSE


ERROR_OCCURRED


ETP-004 Single Responsibility
An event must describe one action only.
Bad:
USER_REGISTERED_AND_LOGGED_IN


Good:
USER_REGISTERED


USER_LOGGED_IN


ETP-005 Traceability
Every event must be traceable to:
* Tenant
* Application
* Environment
* Session
* Run, where captured during a demonstration
* Timestamp
* Source
Supports NFR-DATA requirements.
ETP-006 Single Vocabulary
One concept has one event name. Where two names for the same concept exist, one is canonical and the other is a recognized alias listed in Section 7.0; no third spelling is permitted.
An alias exists only to preserve compatibility with a shipped SDK version. Aliases are not created for new concepts.
ETP-007 Registered Types Only
The platform shall accept only event types registered in Section 7. An unregistered type is rejected at validation rather than stored and ignored.

5.1 Run Correlation
An event captured during a demonstration run carries runId, and the platform assigns it an evidence scope.
PRE_BOUNDARY
Captured after the run was armed but before the initial flow boundary was reached.
IN_FLOW
Captured within the declared flow.
ETD-SCOPE-001
Evidence scope is assigned by the platform from boundary events, not declared by the emitting SDK. An SDK cannot know where a flow begins.
ETD-SCOPE-002
Coverage and reconciliation consume IN_FLOW events only. Both scopes are retained for replay and evidence review.

7.0 Canonical Names And Recognized Aliases
Two spellings entered circulation during Phase 1 development for three concepts. This table resolves them. The canonical name is what documentation, reports and new code use. The alias is accepted at ingestion and normalized to the canonical name before storage.
Concept
	Canonical
	Recognized Alias
	Page navigation
	PAGE_VIEW
	PAGE_VISIT
	Form submission
	FORM_SUBMIT
	FORM_SUBMITTED
	Generic error
	ERROR_OCCURRED
	ERROR_EVENT
	ETD-ALIAS-001
Ingestion shall normalize a recognized alias to its canonical name before storage, so that analysis, reporting and export see one vocabulary.
ETD-ALIAS-002
No new alias shall be introduced. The three above exist because SDK versions carrying them are in the field.
ETD-ALIAS-003
Aliases shall be removed once no supported SDK version emits them, following the deprecation policy in Section 8.

Category H3 — Business Events
Application-defined milestones, emitted explicitly by the customer through the SDK.

The event type is BUSINESS_EVENT; the specific milestone is carried in metadata. This keeps the registered type set closed while allowing customers unlimited domain vocabulary.
ETD-BIZ-002
Business event payloads are subject to the same privacy classification as any other metadata.

8. Event Versioning Strategy
Every event must include:
{
  "eventVersion": "1.0"
}


Rules:
* New fields = Minor version
* Breaking changes = Major version
* Deprecated events retained for migration periods

14. Governance Rules
The ETD is a controlled specification.
Any new event type must:
1. Have a unique identifier.
2. Belong to a defined category.
3. Define a schema.
4. Define ownership.
5. Define retention requirements.
6. Define privacy classification.
7. Define versioning strategy.
8. Be approved through architecture review.
This ensures TELLANN maintains a consistent behavioral language across SDKs, collectors, analytics engines, workflow intelligence systems, production monitoring, and future autonomous behavioral intelligence capabilities.
14.1 Event Registry (Pre-Launch)
The governance rules above describe a controlled vocabulary. Controlling it by review alone is what allowed two spellings of three concepts to enter circulation during Phase 1 development.
A machine-readable event registry shall be maintained as the single source of truth, holding for every registered type:
* Canonical name
* Recognized aliases, if any
* Category
* Owning component
* Metadata schema
* Privacy classification
* Retention class
* Introduced-in version
* Deprecated-in version, if applicable
ETD-REG-001 (Pre-Launch)
Ingestion shall validate every event against the registry, and reject unregistered types rather than storing them.
ETD-REG-002 (Pre-Launch)
The SDK event type union, the collector's validation rules, and this document shall all be derived from the registry, so they cannot disagree.
ETD-REG-003 (Pre-Launch)
Adding a type shall require a registry entry. A type that exists in code but not in the registry is a defect.
Status
Specified. Scheduled for completion and verification before general availability. Section 7.0 records the aliases that exist in the meantime.
