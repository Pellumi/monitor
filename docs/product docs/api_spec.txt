API Specification Document (ASD)
1. Purpose
The API Specification Document (ASD) defines the API contracts for the Self-Observing Testing System (TELLANN).
This document serves as the authoritative reference for:
* SDK communication
* Desktop agent communication
* Telemetry ingestion
* Session management
* Flow declaration and reconciliation
* Codebase and document intelligence
* Instrumentation
* QA run orchestration
* Behavioral graph access
* Coverage analysis
* Missing state analysis
* Endpoint intelligence
* Reporting
* Identity, organization and entitlement management
* Billing and usage
* Notifications
* Administration
* Production intelligence
* Autonomous behavioral intelligence
The APIs defined in this document support all capabilities across:
* Phase 1 — Behavioral QA & Intent Platform
* Phase 2 — Production Monitoring, Feedback & Analysis
* Phase 3 — Autonomous Behavioral Intelligence
1.1 Relationship To The Generated Specification
This document describes API structure, grouping, conventions and phase coverage.
The gateway publishes a machine-readable OpenAPI document that is generated from the running routes. Where the two disagree about the exact shape of a request or response, the generated document is authoritative, because it cannot drift.

This document is authoritative for: which endpoint groups exist, which phase each belongs to, what is delivered versus scheduled, and the conventions every route must follow.

2. API Design Principles
API-001 REST First
All public APIs shall expose REST interfaces.
API-002 OpenAPI Compliance
All APIs shall be reflected in the generated OpenAPI 3.1 document.
API-003 Versioned APIs
Public APIs shall be versioned.
Version Policy
The /v1 prefix marks a contract with an external, independently versioned consumer — the SDKs and the desktop agent — where a breaking change requires a coordinated release.
/v1/events/*
/v1/applications/{id}/flows/*
/v1/applications/{id}/declared-flows/*
/v1/applications/{id}/instrumentation/*
/v1/applications/{id}/intent-drafts/*
Routes consumed only by the first-party dashboard, which deploys with the platform, are served unversioned.
/applications/*
/organizations/*
/sessions/*
/reports/*
/qa-runs/*
/billing/*
API-003a
An unversioned route shall not be consumed by an independently released client. If such a consumer appears, the route is promoted to /v1 first.
API-004 Tenant Isolation
Every request shall be scoped to a tenant.
API-005 Secure by Default
All APIs require authenticated access except health endpoints and the generated specification.
API-006 Traceability
Every request shall support:
{
  "requestId": "",
  "traceId": "",
  "tenantId": ""
}
API-007 Evidence Attribution
Any response carrying an analytical result shall be able to state the evidence it was derived from.

4. Authentication Model
The platform authenticates three distinct classes of caller. They are not interchangeable.
User Session
A human in the dashboard. Bearer access token with refresh.
Device Session
The desktop agent on a specific machine. Bearer access token bound to a registered device, individually revocable.
Ingestion Credential
An SDK embedded in a customer application. Scoped to one application and environment, ingestion only.
Programmatic Token
Scoped machine access to management, reporting, graph, coverage and export APIs. Gated by the API_ACCESS entitlement.
API-AUTH-001
An ingestion credential shall not be able to read analytical results.
API-AUTH-002
A device session shall be individually revocable without affecting the user's other sessions.

Intent / Results Pattern
The platform records an intent to apply or roll back, the desktop agent performs the operation locally, and the agent reports results.
Record Apply Intent
        ↓
Agent Applies Locally
        ↓
Agent Reports Results
This keeps the platform's record of the working tree honest even when the local operation fails or the agent is interrupted.
API-INST-001
A plan shall not reach an applied state without a corresponding results call.

    "reason": "Backend capture track was not enabled for this run"
  }
}
Valid status values:
MEASURED
Evidence was sufficient. A value is present.
INSUFFICIENT_EVIDENCE
Evidence exists but is too thin to report a value.
NOT_MEASURED
No evidence was gathered for this dimension.
API-MEAS-001
A consumer shall be able to distinguish "zero" from "unknown" from every analytical endpoint.
