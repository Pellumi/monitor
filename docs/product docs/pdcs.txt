Privacy & Data Collection Specification (PDCS)
1. Purpose
This document defines the Privacy and Data Collection framework for the Self-Observing Testing System (TELLANN).
The Privacy & Data Collection Specification establishes:
* Data collection principles
* Data classification standards
* Data collection policies
* Collected data definitions
* Masked data definitions
* Ignored data definitions
* Privacy enforcement architecture
* SDK privacy controls
* Session replay privacy controls
* Tenant privacy controls
* Data retention policies
* Compliance requirements
* Phase-based privacy evolution
The objective of this specification is to ensure that TELLANN can generate behavioral intelligence while protecting user privacy, preventing unauthorized collection of sensitive information, and maintaining enterprise trust.
This specification governs all data collected, processed, stored, analyzed, transmitted, exported, or displayed throughout the platform lifecycle. It applies across SDKs, ingestion systems, analytics engines, behavioral graphs, session replay, reporting systems, production monitoring systems, and autonomous intelligence systems.

Sensitive information shall never enter the platform whenever possible.

8. Masked Data Specification (Pre-Launch)
Masked data may be collected only after masking, hashing, tokenization, or redaction.
Status
Specified. Scheduled for completion and verification before general availability.
Current behavior: the SDKs exclude sensitive fields by name and never capture password inputs (Section 11), and the desktop agent classifies and protects sensitive captured values (Section 12.1). The field-level transformation rules in 8.1 through 8.8 — hashing, pseudonymization, partial masking and redaction of the values that are captured — are not yet applied.
PDCS-MASK-001
Until this section is delivered, the platform shall not represent PII masking as available in any customer-facing surface, and the data collection matrix in Section 18 shall be read as the target state rather than the current state.

12.1 Local Agent Privacy Controls
The desktop agent introduces privacy surfaces that do not exist in an SDK-only product. It reads customer source code, drives a browser session that passes through real credentials, and writes to a customer working tree.
Local-First Principle
PDCS-LOCAL-001
Customer source code shall be processed on the developer's machine. Only derived artifacts — code graph projections, analysis warnings, checkpoint locations — shall be transmitted by default.
PDCS-LOCAL-002
Raw source, source archives and unreviewed working-tree diffs shall be transmitted only on explicit consent granted for a named purpose.
PDCS-LOCAL-003
A consent grant shall record what was consented to, for what purpose, by which user, and when.
PDCS-LOCAL-004
Consent shall be per-purpose and shall not generalize. Consenting to upload an archive for one analysis does not consent to the next.
Workspace Trust
PDCS-LOCAL-005
A bound workspace shall carry a trust status, and the agent shall refuse privileged operations against an untrusted workspace.
PDCS-LOCAL-006
The agent shall detect and refuse to operate where the bound repository does not match the application it is bound to.
Protected Values
A demonstration run passes through login forms, payment fields and API payloads containing values that must not be stored in the clear.
Captured
    ↓
Classified
    ↓
Stored Protected
    ↓
Revealed Only On Explicit Request
    ↓
Reveal Audited
PDCS-LOCAL-007
Values classified as protected shall never appear in evidence, replay, findings, reports or exports in the clear.
PDCS-LOCAL-008
A reveal shall require an authenticated, authorized user, and shall be recorded in the audit log with the revealing user and the value revealed.
PDCS-LOCAL-009
Credentials supplied to drive a run shall be held in operating-system protected storage on the developer's machine and shall never be transmitted to the platform.
Working Tree Safety
PDCS-LOCAL-010
Diffs displayed or exported shall be redacted of secrets before rendering.
PDCS-LOCAL-011
No write to a customer working tree shall occur without an approved plan, and every applied plan shall be reversible.
Device Identity
PDCS-LOCAL-012
A desktop session shall be bound to a device and shall be individually revocable without affecting the user's other sessions.
PDCS-LOCAL-013
A user shall be able to see every device holding a session and revoke any of them.

13. Privacy Rule Engine (Pre-Launch)
Customers may define custom privacy rules.
Status
Specified. Scheduled for completion and verification before general availability.
Current behavior: the SDKs enforce a sensitive-key denylist and password-field exclusion (Sections 11 and 12), and the desktop agent enforces protected-value classification (Section 12.1). Customer-defined rules are not yet configurable.
Example:
{
  "field": "customerEmail",
  "action": "HASH"
}


Supported Actions:
* IGNORE
* MASK
* HASH
* TOKENIZE
* REDACT
PDCS-RULE-001
Until the rule engine is delivered, the platform shall not represent customer-defined privacy rules as available in any customer-facing surface.

19. Privacy Acceptance Criteria
The Privacy & Data Collection Specification shall be considered complete when:
1. All collected data categories are explicitly defined.
2. All masked data categories are explicitly defined.
3. All ignored data categories are explicitly defined.
4. Sensitive information cannot enter the analytics pipeline.
5. Session replay respects privacy controls.
6. SDKs enforce privacy rules before transmission.
7. Tenant-specific privacy rules are supported.
8. Data retention policies are enforceable.
9. Data exports respect privacy controls.
10. Customer source code does not leave the developer's machine without purpose-named consent.
11. Protected values are never rendered in the clear, and every reveal is audited.
12. Assisted intelligence input is sanitized before transmission and every invocation is logged.
13. The platform can generate behavioral intelligence, production intelligence, and autonomous behavioral intelligence without exposing sensitive customer information.
20. Pre-Launch Privacy Checklist
The following are specified in this document and scheduled for completion and verification before general availability. This list is the review checklist.
* Masked Data Specification — Section 8. Field-level hashing, pseudonymization, partial masking and redaction of captured values.
* Privacy Rule Engine — Section 13. Customer-defined rules with IGNORE, MASK, HASH, TOKENIZE and REDACT actions.
* Tenant-configurable retention — Section 14, PDCS-RET-001.
* Section 18 data collection matrix verified against actual behavior, with every row confirmed rather than intended.
PDCS-LAUNCH-001
Until each item above is delivered and verified, no customer-facing surface, marketing claim, or contractual commitment shall represent it as available.
PDCS-LAUNCH-002
This checklist shall be reviewed as a whole before general availability. Partial delivery of Section 8 is not delivery of Section 8.
