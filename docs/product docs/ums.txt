Usage Metering Specification (UMS)
1. Purpose
This document defines how usage is measured, tracked, enforced, reported, and monetized across the TELLANN platform.
The Usage Metering Specification establishes:
* Usage metrics
* Billable units
* Non-billable units
* Quota enforcement rules
* Overage framework
* Future pricing evolution
* Usage reporting standards
* Billing data requirements
The UMS serves as the authoritative source for all platform metering decisions.
2. Metering Philosophy
TELLANN measures significantly more than it bills.
The platform captures:
* Events
* Sessions
* Demonstrations
* Workflow graphs
* Reports
* Replay assets
* Storage consumption
These measurements support:
* Product analytics
* Capacity planning
* Abuse prevention
* Future pricing evolution
Measurement does not imply billing.
During Phase 1, only a subset of measured resources are customer-facing billing metrics.

4. Billable Metrics (Phase 1)
Applications
Definition
A unique onboarded application registered within an organization.
Source:
Application Management Service
Examples:
* Web App
* Mobile App
* Admin Portal
* API Platform
Measurement Unit:
Application
Example:
Acme Corp
* Storefront
* Admin Portal
* Mobile App
Usage = 3 Applications
Users
Definition
An active user with access to an organization.
Includes:
* Owners
* Admins
* Members
* Viewers
Measurement Unit:
User Seat
Calculation:
Active organization members plus unexpired invitations, evaluated at the point of enforcement.
An invitation consumes a seat from the moment it is issued, because a seat that can be claimed at any time is a seat that is committed. Expiring or revoking an invitation returns the seat.
Quota enforcement is evaluated against current occupancy rather than a period peak. A customer who removes a member can immediately invite a replacement; they are not held to a high-water mark they have already reduced.
UMS-SEAT-001
The seat figure used for quota enforcement and the seat figure shown in the usage dashboard shall be the same figure, computed the same way.
Storage
Definition
Total stored customer assets.
Includes:
* Events
* Sessions
* Replay Assets
* Reports
* Graph Snapshots
* Exports
Measurement Unit:
Gigabytes (GB)
Calculated Daily.
Billing uses monthly peak usage.
Retention
Definition
Maximum duration customer data is preserved.
Retention is controlled by plan entitlement rather than consumption.
Measurement Unit:
Days
Examples:
* 14 Days
* 90 Days
* 180 Days
* 365 Days
5. Measured But Non-Billable Metrics
These metrics are collected but do not impact Phase 1 billing.
Events
Definition
Canonical telemetry events captured by SDKs and the desktop agent.
Examples:
* PAGE_VIEW
* BUTTON_CLICK
* FORM_SUBMIT
* API_REQUEST
* FLOW_STATE_REACHED
Purpose:
* Capacity Planning
* Abuse Detection
* Future Event Pricing
Customer Cost Impact:
None (Phase 1)
Demonstration Sessions
Definition
Recorded demonstration runs, driven by the desktop agent.
Examples:
* Guided Run
* Assisted Run
* Observation Only Run
Purpose:
* Product Analytics
* Capacity Forecasting
Customer Cost Impact:
None on paid plans.
Free Plan may impose limits.
Sessions
Definition
Completed reconstructed behavioral sessions.
Purpose:
* Operational visibility
* Storage forecasting
Customer Cost Impact:
None
Session Replays
Definition
Generated replay assets associated with recorded sessions.
Purpose:
* Storage planning
* Replay infrastructure sizing
Customer Cost Impact:
Indirect via storage limits only.
Behavioral Graphs
Definition
Generated workflow intelligence models.
Measured:
* States
* Transitions
* Workflows
Purpose:
* Intelligence generation metrics
* Future platform analytics
Customer Cost Impact:
None
Reports
Definition
Generated QA reports.
Examples:
* Coverage Reports
* Missing Flow Reports
* Reconciliation Reports
* Run Reports
* Endpoint Reports
Purpose:
* Platform analytics
* Capacity forecasting
Customer Cost Impact:
None
Exports
Definition
Report downloads in any entitled format.
Purpose:
* Platform analytics
* Abuse detection
Customer Cost Impact:
None. Format availability is an entitlement, not a quota.
API Calls
Definition
Requests made using a programmatic access token.
Purpose:
* Capacity planning
* Abuse detection
* Rate limit enforcement
Customer Cost Impact:
None in Phase 1. Programmatic access itself is gated by entitlement.
Assisted Intelligence Consumption
Definition
Model invocations made on a customer's behalf — flow drafting, suggestion enrichment, domain inference, output repair.
Measured:
* Invocation count by feature
* Token consumption
* Provider cost
* Success and failure status
Purpose:
* Capacity planning
* Cost control
* Feature viability assessment
Customer Cost Impact:
None in Phase 1.
UMS-AI-001
Assisted consumption is metered from the first invocation, even though it is not billed, so that Phase 3 AI billing can be introduced against real historical data rather than an estimate.
UMS-AI-002
Assisted consumption shall be attributable to an organization, a feature and an invoking user.
UMS-AI-003
Assisted consumption shall be visible to platform administrators. It shall not be surfaced to customers as a consumable balance in Phase 1, because presenting a meter for something that is not billed and cannot be exhausted creates a constraint that does not exist.
6. Phase 1 Quota Enforcement
Quota enforcement shall occur at the organization level.
Hard Limits:
* Applications
* Users
* Storage
* Environments per application
* Ingestion credentials
Soft Limits:
* Reports
* Sessions
* Demonstrations
* Events
* Exports
* API calls
* Assisted intelligence consumption
Enforcement Thresholds
Administrators are warned at 80% of a hard limit.
Quota-consuming operations are blocked at 100%.
Existing data remains readable and exportable, and billing, deletion and upgrade access are retained.
Example:
Storage exceeds plan limit:
Status:
READ_ONLY_WARNING
Grace Period:
14 Days
After Grace Period:
Upgrade Required

Phase 1
No automatic overage billing.

* Warning Notifications
* Grace Period

Reason:
Maintain pricing simplicity.
10. Phase 2 Event Metering
Phase 2 introduces production monitoring.

Definition:
Any validated event ingested from production environments.
Examples:
* PAGE_VIEW
* API_REQUEST
* STATE_TRANSITION
* ERROR_OCCURRED
Demonstration Events remain excluded.
Included Event Pools
Example:
Team Plan
Included:
5,000,000 Events
Overage:
$5 per Additional 1,000,000 Events
11. Phase 3 AI Metering
Phase 3 is the first phase in which AI consumption becomes a customer-facing billing metric.
Billable AI Capabilities
* Test Generation
* Regression Analysis
* Failure Simulation Analysis
* Quality Assessments
* Remediation Proposals
* Network Divergence Analysis
* Intelligence Assistant Queries
Not Billable
The Phase 1 assisted capabilities — flow drafting, suggestion enrichment, domain inference, output repair — remain non-billable. They are part of declaring intent, and charging a customer to describe their own software is a tax on onboarding.
AI usage must remain transparent.
Opaque credit systems are prohibited.
Every billable AI operation shall display:
* Usage Consumed
* Cost Impact
* Billing Category
UMS-AI3-001
A customer shall be able to see what an AI operation will consume before invoking it.
UMS-AI3-002
A failed AI operation shall not consume billable units.
12. Usage Governance
All metered units must:
* Be measurable
* Be auditable
* Be reproducible
* Be tenant scoped
* Be visible to customers
No hidden billable metrics are permitted.
No undocumented billing dimensions are permitted.
12.1 Internal Metric Disclosure
An internal-only metric is not a hidden billable metric. It is a metric that is measured and not charged for.
UMS-GOV-001
No internal-only metric shall affect what a customer is charged, directly or indirectly, without being promoted to a customer-facing metric and documented here first.
UMS-GOV-002
Promoting a metric from internal to customer-facing is a pricing change and requires review under the Pricing & Packaging Specification, Section 14.
UMS-GOV-003
The complete list of measured metrics — billable and not — is Sections 4 and 5 of this document. There is no third list.
13. Success Criteria
The Usage Metering System shall be considered successful when:
1. Customers understand usage limits immediately.
2. Phase 1 billing remains simple.
3. Platform usage is fully observable internally.
4. Future event pricing can be introduced without redesign.
5. Future AI pricing can be introduced without redesign.
6. All billable metrics are transparent.
7. Usage disputes can be resolved through auditable records.
8. Metering remains aligned with customer value.
