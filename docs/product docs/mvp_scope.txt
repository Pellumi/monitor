MVP Scope Document (MSD)
1. Purpose
This document defines the exact scope of the TELLANN Minimum Viable Product (MVP).
The objective is to:
* Prevent feature creep
* Establish implementation boundaries
* Define what will be delivered
* Define what will not be delivered
* Align engineering, product, and business expectations
* Reduce implementation risk
* Accelerate time-to-market
This document is the authoritative source for Phase 1 feature inclusion and exclusion decisions.
Any functionality not explicitly listed as Included shall be considered Out of Scope unless approved through formal scope review.
2. MVP Vision
The MVP exists to prove a single hypothesis:
A team can state what their software is supposed to do, demonstrate it once, and have the platform show them the difference.
The MVP is not intended to:
* Replace QA teams
* Replace observability platforms
* Replace analytics platforms
* Provide autonomous testing
* Monitor production traffic
* Generate software on the user's behalf
Instead, the MVP demonstrates that declared intent and observed behavior can be reconciled automatically into actionable quality intelligence.

4. MVP Business Objective
The MVP must allow a team to:
1. Declare the flows an application is intended to support
2. Connect a local codebase through the Tellann desktop agent
3. Instrument the application under explicit review
4. Demonstrate the application through a guided browser run
5. Generate behavioral intelligence from that run
6. Reconcile declared intent against observed behavior
7. Understand workflow coverage
8. Identify missing states and missing flows
9. Analyze API behavior
10. Replay sessions
11. Export QA reports
The platform must demonstrate value immediately after a single guided run.

6.1 Where Demonstration Runs
Demonstration is driven by the Tellann desktop agent, not by the browser dashboard.
A QA run requires:
* A device-bound desktop session
* A bound local workspace
* An instrumented application
* A run target URL
The dashboard cannot start a run. It presents run history, evidence, reconciliation, and reports, and hands off to the desktop agent when a user asks to start a demonstration.
Rationale:
* Flow boundaries, evidence scoping, and protected-value handling require a controlled browser.
* Instrumentation must be applied to a real working tree under human review.
* Raw source never leaves the developer's machine without explicit consent.

9.1 Assisted Intelligence Boundary
Earlier revisions of this document excluded artificial intelligence from Phase 1 entirely. That exclusion is replaced by a boundary rather than a ban, because the capability that was actually needed — helping a human state what their software is supposed to do — is not the capability that was being guarded against.
The guard remains. It is now specific.
Permitted in Phase 1
* Drafting candidate flows from documents the customer supplied
* Suggesting branch states where the deterministic rule library returns no match
* Inferring an application domain to select a rule pack
* Repairing malformed structured output from a model
Prohibited in Phase 1
* Producing a behavioral graph
* Producing coverage, reconciliation or missing-state results
* Producing report findings or severity
* Producing quality scores or risk judgements
* Adding anything to a Declared Intent Graph without explicit human acceptance
* Modifying customer source without an approved, reviewable, reversible plan
Governing Rules
MSD-AI-001
Assisted intelligence proposes. Humans dispose. No model output enters a Declared Intent Graph, a ruleset, or a report without an explicit human acceptance action.
MSD-AI-002
The deterministic path is primary. The internal pattern library and structural matching are consulted first. A model is consulted only where they return no usable result.
MSD-AI-003
Every analytical output the platform publishes — graphs, coverage, reconciliation, findings, endpoint analysis — is computed from recorded evidence by deterministic code, and must be reproducible from the same evidence.
MSD-AI-004
Removing the model provider shall degrade the quality of assistance. It shall not stop the product from functioning. Declaration remains possible by hand, and every analytical capability continues to operate unchanged.
MSD-AI-005
Every model invocation is logged with its feature, status, attribution and cost, and is visible to platform administrators.
MSD-AI-006
Assisted intelligence is never marketed as the product. The product is behavioral evidence.
The Wrapper Test
At any point in Phase 1, the following must remain true:
Disable the model provider.
The platform still declares, instruments, demonstrates,
reconciles, measures and reports.
Only suggestion quality is reduced.
If that ceases to be true, scope has drifted and requires formal review.
9.2 Quality Scores
Composite quality scores are excluded from Phase 1.
The platform reports measured evidence and the state of that measurement. It does not synthesize a single number representing software quality from a single demonstration.
See the QA Report Specification, Section 26, for the evidence-state model that replaces scoring.
Composite scoring returns in Phase 3, when the platform has continuous production evidence and cross-release history to justify it.
10. Phase 1 Structural Groundwork
Phase 1 deliberately ships a small amount of structure belonging to later phases. This is scope-controlled and intentional: it validates the architecture early and lets customers see the direction of travel.
Included as groundwork
* Graph drift — comparison of behavioral graph versions over time, and coverage history trend. Phase 2 extends this to production baselines; Phase 3 extends it to anomaly detection.
* Cross-tenant structural pattern index — anonymized graph shape aggregation, already governed by FDRS-PRIV-001 through FDRS-PRIV-004. Phase 3 extends this to network-wide behavioral intelligence.
* Assisted intelligence — bounded per Section 9.1. Phase 3 extends this to behavioral reasoning.
* Recommendation evidence and rule candidates — evidence capture and promotion pipeline for platform rules. Phase 3 extends this to implementation suggestions.
Explicitly not included as groundwork
* Any production traffic ingestion
* Any automated change to a customer system
* Any composite quality judgement
Groundwork Rule
MSD-GW-001
A groundwork capability may be shipped only where it is useful on Phase 1 evidence alone. Capability that requires production data or cross-release history to be meaningful is deferred, not stubbed.
11. MVP Success Criteria
The MVP is considered successful when a team can:
1. Declare an intended flow.
2. Install the desktop agent and bind a local workspace.
3. Apply reviewed instrumentation to that workspace.
4. Complete a guided demonstration run.
5. Generate a behavioral graph.
6. Discover workflows automatically.
7. View session replay.
8. Measure workflow coverage.
9. Reconcile declared intent against observed behavior.
10. Identify missing flows.
11. Identify missing states.
12. Analyze API performance.
13. Export QA reports.
Without requiring:
* Production traffic
* Historical telemetry
* Machine learning models
* Manual workflow modeling of observed behavior
* Any model provider being reachable
12. MVP Exit Criteria
Phase 1 is complete when:
* All included features are implemented.
* All excluded features remain excluded.
* The declare → demonstrate → reconcile → report loop operates end to end.
* Desktop-driven guided runs complete reliably and produce reports.
* Instrumentation can be applied, validated and rolled back safely.
* Behavioral graphs generate successfully.
* Reconciliation reports generate successfully.
* Coverage reports generate successfully.
* Session replay functions correctly.
* QA reports are exportable in all entitled formats.
* Dashboard provides complete Phase 1 visibility.
* The Wrapper Test in Section 9.1 passes.
At that point the platform can begin Phase 2 development.

14. Phase Roadmap Summary
Phase 1 — Behavioral QA & Intent Platform
Declare what the software should do. Demonstrate it once. See the difference.
Phase 2 — Production Monitoring, Feedback & Analysis
Observe the customer's system in production with real users, and convert that into guidance on what to build, fix or change next.
Phase 3 — Autonomous Behavioral Intelligence
Understand a running system continuously, remediate in real time as end users encounter problems, and use network-wide behavioral intelligence to propose implementation changes.
Full definitions are held in the Functional Requirements Specification, Section 2.
