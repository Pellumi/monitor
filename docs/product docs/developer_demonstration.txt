Developer Demonstration Mode Specification (DDMS)
1. Purpose
This document defines the Developer Demonstration Mode (DDM) for the Self-Observing Testing System (TELLANN).
Developer Demonstration Mode is the primary workflow through which developers introduce an application to TELLANN and obtain immediate quality intelligence without requiring production traffic, historical telemetry, or model training.
Developer Demonstration Mode is the foundational capability of the Behavioral QA & Intent Platform and serves as the entry point for all future intelligence capabilities.
The purpose of DDM is to transform a developer-recorded application walkthrough into:
* Behavioral Graphs
* Workflow Maps
* Coverage Reports
* Missing State Reports
* Missing Flow Reports
* Reconciliation Reports
* Endpoint Analysis
* QA Run Reports
* Future Production Comparison Baselines
This capability represents the primary differentiator of Phase 1 and establishes the behavioral baseline required for all future platform phases.
2. Scope
Developer Demonstration Mode applies across all platform phases.
Phase 1 — Behavioral QA & Intent Platform
Used to generate:
* Behavioral Graphs
* Coverage Reports
* Missing State Reports
* Reconciliation Reports
* Endpoint Analysis
* QA Reports
Phase 2 — Production Monitoring, Feedback & Analysis
Used to establish baseline workflow models against which production behavior is compared, and to reproduce production findings under controlled conditions.
Phase 3 — Autonomous Behavioral Intelligence
Used as verification evidence for:
* Test Generation
* Regression Detection
* Failure Simulation
* Real-Time Remediation Validation

4. Conceptual Model
Developer Demonstration Mode follows a simple principle:
Developer Declares Intent
                ↓
Developer Demonstrates Application
                ↓
TELLANN Observes Behavior
                ↓
TELLANN Builds Workflow Model
                ↓
TELLANN Reconciles Intent Against Observation
                ↓
TELLANN Identifies Coverage
                ↓
TELLANN Identifies Missing Paths
                ↓
TELLANN Generates QA Intelligence
The developer is not writing tests.
The developer is teaching the platform how the application behaves, and confirming whether that matches what was intended.
5. Execution Environment
Demonstration is driven by the Tellann desktop agent.
The desktop agent is a locally installed application that holds a device-bound platform session, binds to a local codebase, applies instrumentation under review, and drives a managed browser session in which the walkthrough is performed.
DDM-ENV-001
A demonstration run shall be startable only from the Tellann desktop agent.
DDM-ENV-002
The dashboard shall not expose an endpoint capable of opening a run. Where a user requests a demonstration from the dashboard, the dashboard shall hand off to the desktop agent.
DDM-ENV-003
A run shall require a bound local workspace, an instrumented application, a resolvable run target, and an authenticated device session.
DDM-ENV-004
Raw source shall remain on the developer's machine unless the developer explicitly consents to an upload for a named purpose.
Rationale
Flow boundary detection, evidence scoping, protected-value handling and reversible instrumentation all require control over the browser and the working tree. A browser-only integration cannot provide any of them.
Consequence
Demonstration quality no longer depends on a developer remembering to start and stop a recording in their own browser. The environment is deterministic, and the evidence is bounded by flow boundaries rather than by wall-clock time.

7. Demonstration Session Model
Definition
A Demonstration Session is a recorded developer walkthrough, driven by the desktop agent, used to teach TELLANN how the application behaves.
Session Structure

  "applicationId": "uuid",
  "environmentId": "uuid",

7.1 Run Modes
Guided
The platform holds a declared flow and walks the developer through it, confirming boundaries and prompting for the states it expects to see.
Use when: a declared flow exists and the goal is to verify it.
Assisted
The developer navigates freely. The platform observes, identifies which declared flow the activity most resembles, and surfaces expectations without directing.
Use when: intent is partially declared, or the developer is exploring.
Observation Only
The platform records without prompting or directing, and restricts itself to read-safe interactions.
Use when: the target is sensitive, shared, or must not be altered.
DDM-MODE-001
Every run shall record its mode. Reports shall state the mode under which evidence was gathered, because the mode affects what absence of evidence means.
7.2 Capture Tracks
Frontend
Browser-side behavior from the managed session and the frontend SDK.
Backend
Server-side behavior from the backend SDK, correlated to the run session.
A run may enable either or both. A run with only the frontend track produces no endpoint intelligence, and reports shall say so rather than reporting zero.
7.3 Run Lifecycle States
CREATED
ARMED
WAITING_FOR_INITIAL
RECORDING
RUNNING
PAUSED
PROCESSING
COMPLETED
COMPLETED_INCOMPLETE
FAILED

COMPLETED_INCOMPLETE is a first-class outcome. A run whose browser closed before a terminal state was reached still produced evidence, and that evidence is still reported — labelled as incomplete rather than discarded.
8. Flow Boundaries And Evidence Scope
A demonstration run does not treat all captured activity as equal.
Run Armed
     ↓
Pre-Boundary Activity     ← setup, login, navigation to the start
     ↓
Initial Flow Boundary Reached
     ↓
In-Flow Activity          ← the evidence the report is built from
     ↓
Terminal State Reached
Every evidence event carries a scope:
PRE_BOUNDARY
Activity before the declared flow began. Retained for context and replay. Excluded from coverage calculation.
IN_FLOW
Activity within the declared flow. This is the evidence coverage and reconciliation are computed from.
DDM-BOUND-001
Coverage and reconciliation shall be computed from in-flow evidence only.
DDM-BOUND-002
A run that ends before the initial boundary is reached shall produce a report stating that no in-flow evidence was gathered, rather than a zero-coverage result.
DDM-BOUND-003
Pre-boundary evidence shall remain available in replay and evidence views.
Rationale
Without boundaries, the time a developer spends logging in and finding the right page is indistinguishable from the workflow under test, and coverage becomes a function of how much unrelated navigation happened to be recorded.
9. Protected Values
A demonstration inevitably passes through fields and payloads containing values that must not be stored in the clear.
Handling
Detected At Capture
       ↓
Classified
       ↓
Stored Protected
       ↓
Revealed Only On Explicit Request
       ↓
Reveal Audited
DDM-PROT-001
Values classified as protected shall never appear in evidence, replay, findings or exports in the clear.
DDM-PROT-002
A reveal action shall require an authenticated, authorized user and shall be recorded in the audit log.
DDM-PROT-003
Credential material required to drive a run shall be held by the desktop agent and shall not be persisted to platform storage.
Consistent with the Privacy & Data Collection Specification.

14. Reconciliation
Where a Declared Intent Graph exists, the demonstration is reconciled against it.
Declared States:     14
Observed States:     12
Confirmed:           11
True Gaps:            3
Undeclared:           2
Confirmed
Declared and observed. Evidence-backed coverage.
True Gap
Declared and never observed. A human asserted this should be reachable and the demonstration did not reach it.
Undeclared
Observed and never declared. The application did something nobody specified.
Promotion
Where a demonstration produces an undeclared state, the platform may prompt the developer:
This state wasn't in your declared flow — is it expected?
An affirmative response promotes the state into the Declared Intent Graph with provenance DEMONSTRATION_PROMOTED and triggers ruleset recompilation.
DDM-RECON-001
Promotion shall require explicit developer confirmation and shall never occur automatically.
Specified in full by the Behavior Graph Specification, Section 22.5 and 22.7.

25. Success Criteria
Developer Demonstration Mode shall be considered successful when a developer can:
1. Declare an intended flow.
2. Install the desktop agent and bind a local workspace.
3. Apply reviewed instrumentation and roll it back.
4. Complete a guided demonstration run.
5. Automatically obtain a behavioral graph.
6. Automatically obtain workflow coverage.
7. Automatically reconcile intent against observation.
8. Automatically identify missing states.
9. Automatically identify missing flows.
10. Automatically receive QA recommendations.
11. Establish a baseline for production intelligence.
12. Do all of the above without customer source leaving the machine.
