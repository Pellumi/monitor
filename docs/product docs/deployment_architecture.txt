Deployment Architecture Specification (DAS)
1. Purpose
The Deployment Architecture Specification (DAS) defines how the Self-Observing Testing System (TELLANN) is deployed, operated, scaled, secured, upgraded, and maintained across all supported environments.
This document establishes:
* Deployment models
* Infrastructure architecture
* Cloud architecture
* Self-hosted architecture
* Network architecture
* Multi-tenant architecture
* Kubernetes architecture
* Data platform deployment
* Analytics platform deployment
* Security architecture
* Disaster recovery architecture
* Scalability architecture
* Environment strategy
* CI/CD architecture
* Observability architecture
* Phase-based deployment evolution
The objective of this specification is to ensure TELLANN can operate reliably from early-stage MVP deployments through large-scale enterprise installations while maintaining architectural consistency across all phases of the product lifecycle.
2. Scope
This specification applies to:
Phase 1 — Behavioral QA & Intent Platform
Deployment of:
* Frontend SDK Infrastructure
* Backend SDK Infrastructure
* Event Collection Platform
* Session Replay Services
* Behavioral Graph Services
* Coverage Analysis Services
* Reconciliation Services
* Code Intelligence Services
* QA Reporting Services
* Dashboard, Marketing and Documentation Services
* Platform Services — auth, onboarding, billing, usage, notifications
Distribution of:
* Tellann Desktop Agent
The desktop agent is distributed to developer machines rather than deployed to infrastructure. It is in scope for this document because it must be built, signed, released and updated, and because the platform's compatibility obligations to it constrain how services may change. See Section 17.1.
Phase 2 — Production Monitoring, Feedback & Analysis
Additional deployment of:
* Live Monitoring Services
* Journey Intelligence Services
* Database Intelligence Services
* Error Correlation Services
* Workflow Health Monitoring Services
Phase 3 — Autonomous Behavioral Intelligence
Additional deployment of:
* Test Generation Services
* Regression Detection Services
* Failure Simulation Services
* Optimization Intelligence Services
* Quality Intelligence Services
* Intelligence Assistant Services
3. Deployment Principles
DAS-001 Cloud Native First
All platform services shall be containerized.
DAS-002 Kubernetes Native
All platform services shall be deployable on Kubernetes.
DAS-003 Multi-Tenant by Default
Deployment architecture shall support tenant isolation.
DAS-004 Horizontal Scalability
Every major service shall support horizontal scaling.
DAS-005 Observability by Default
Every deployed component shall emit:
* Logs
* Metrics
* Traces
DAS-006 Zero Trust Security
All service communication shall be authenticated and encrypted.
DAS-007 Deployment Independence
Services shall be independently deployable.

17.1 Desktop Agent Distribution
The desktop agent is the one component that is not deployed. It is shipped.
Build
    │
    ▼
Sign
    │
    ▼
Publish To Release Channel
    │
    ▼
Update Feed
    │
    ▼
Developer Machine Checks Feed
    │
    ▼
Update Downloaded And Verified
    │
    ▼
Applied Under Policy
Distribution
* Signed installers per supported platform
* Custom protocol handler registration for setup handoff from the dashboard
* Authenticated update feed
Release Channels
Stable
The default. What customers download.
Beta
Opt-in, for customers validating an upcoming agent against their own codebase.
Version Independence
The agent and the platform version independently, because the platform can be deployed in an afternoon and an agent takes as long as customers take to update.
DEP-AGENT-001
The platform shall remain compatible with every agent version still supported in the field.
DEP-AGENT-002
An agent shall degrade gracefully against a newer platform rather than failing.
DEP-AGENT-003
The platform shall be able to declare an agent version unsupported, and the agent shall refuse to operate when it is.
DEP-AGENT-004
Update packages shall be signature-verified before application, and the update feed shall not be redirectable by local configuration.
Deployment Consequence
A breaking change to any endpoint the agent consumes is a coordinated release, not a routine deploy. Those endpoints carry the /v1 prefix for exactly this reason. See the API Specification, Section 2, API-003.
17.2 Multi-Application Deployment
Three web applications deploy independently on separate domains.
domain.com
    Marketing site. Public, unauthenticated.

app.domain.com
    Dashboard. Authenticated product surface.

docs.domain.com
    Documentation. Public, unauthenticated.

api.domain.com
    API Gateway. SDK ingestion and desktop agent traffic.
DEP-APP-001
Authentication cookies shall be scoped to the application domain and shall not be shared with the marketing or documentation domains.
DEP-APP-002
Each application shall be independently deployable. A marketing content change shall not require a product deployment.

Goal:
Establish what an application is supposed to do, observe what it does under demonstration, and report the difference.
Phase 2 — Production Monitoring, Feedback & Analysis
Additional Services:
Production Ingestion Path
Workflow Health Monitor
Journey Intelligence Engine
Database Intelligence Engine
Error Correlation Engine
Guidance Engine


Deployment change required:
The ingestion path must separate production evidence from demonstration evidence at collection time. They are metered differently, retained differently, and compared against one another, so they cannot share a topic and be untangled later.
Expect ingestion volume to change by orders of magnitude. Phase 1 volume is bounded by how often developers run demonstrations; Phase 2 volume is bounded by how many end users a customer has.
Goal:
Continuously understand production behavior and convert it into guidance.
Phase 3 — Autonomous Behavioral Intelligence
Additional Services:
Test Generation Engine
Regression Engine
Failure Simulation Engine
Optimization Engine
Behavioral Anomaly Engine
Network Behavioral Intelligence
Remediation Engine
Authority & Policy Service
Quality Intelligence Engine
Intelligence Assistant


Deployment change required:
An authority service that is consulted before any autonomous action and whose revocations take effect immediately. Authority cannot be cached.
Failure Simulation requires isolated execution that cannot reach a customer's production system except where the customer has explicitly granted it.
Goal:
Understand a running system continuously, and act on that understanding under customer authority.

27. Deployment Invariants
DEP-INV-001
The desktop agent is never deployed to the cluster. It ships to developer machines and updates on its own cadence.
DEP-INV-002
Customer source never reaches platform infrastructure except as an explicitly consented archive.
DEP-INV-003
Endpoints consumed by the desktop agent or the SDKs are versioned, and breaking changes to them are coordinated releases.
DEP-INV-004
The three web applications deploy independently and do not share authentication cookies.
DEP-INV-005
A model provider outage degrades assistance and nothing else. No deployment topology shall make an analytical service depend on provider availability.
