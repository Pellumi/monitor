QA Report Specification (QRS)
1. Purpose
This document defines the Quality Assurance Reporting Framework for the Self-Observing Testing System (TELLANN).
The QA Report Specification establishes:
* Report architecture
* Report generation standards
* Report categories
* Report structures
* Report metrics
* Report scoring models
* Report lifecycle management
* Report versioning
* Phase-based reporting evolution
The purpose of the reporting system is to transform captured behavioral data into actionable quality intelligence that enables software teams to understand application quality without manually analyzing telemetry, workflows, sessions, or production data.
The QA Reporting System serves as the primary communication layer between TELLANN intelligence engines and engineering teams.
2. Scope
This specification applies to all reports generated by TELLANN.
Phase 1 — Behavioral QA & Intent Platform
Behavioral QA and reconciliation reports
Phase 2 — Production Monitoring, Feedback & Analysis
Production intelligence and guidance reports
Phase 3 — Autonomous Behavioral Intelligence
Autonomous quality intelligence and remediation reports

4.1 Report Addressing
Phase 1 serves reports in two forms.
Application Report
The current analytical state of an application, derived on request from the latest evidence. Addressed by application.
Run Report
The report produced by one demonstration run. Addressed by run, generated asynchronously, retryable.
A versioned catalogue of independently addressable report objects, carrying the metadata standard in Section 5, is scheduled for completion before general availability. See the API Specification, Section 24.1.

QRS-RECON-001
Every True Gap shall state whether the originating node was USER_AUTHORED or SUGGESTED_ACCEPTED, to distinguish "the team specifically asked for this and it is missing" from "the system proposed it and it does not exist yet".
QRS-RECON-002
Undeclared observations shall be presented as a distinct category for human review, not folded into missing-state or missing-flow findings, and not treated as errors by default.

26. Measurement & Scoring Framework
26.1 Position
Composite quality scores are deferred to Phase 3.
A single number between 0 and 100 claiming to represent the quality of a piece of software is a claim about evidence. From one demonstration run, that claim cannot be supported. A team that ships a fix and watches the number move without understanding why has been given confidence, not information.
Phase 1 therefore reports measured values and the state of their measurement, and reserves composite scoring until continuous production evidence and cross-release history exist to justify it.
26.2 Evidence State Model
Every reported value carries a measurement state.
{
  "stateCoverage": {
    "status": "MEASURED",
    "value": 76.4,
    "delta": 3.1,
    "basis": "1 guided run, in-flow evidence"
  }
}
Valid states:
MEASURED
Evidence was sufficient. A value is present, and a delta against the previous measurement where one exists.
INSUFFICIENT_EVIDENCE
Evidence exists but is too thin to report a value honestly.
Rendered as: "Not enough evidence"
NOT_MEASURED
No evidence was gathered for this dimension.
Rendered as: "Not measured yet"
QRS-MEAS-001
A report shall never render an unmeasured dimension as zero. Zero is a measurement.
QRS-MEAS-002
Every measured value shall be able to state the evidence basis it was computed from: run count, run mode, capture tracks, evidence scope, and whether a declared baseline existed.
QRS-MEAS-003
A dimension that could not be measured shall state why. "Backend capture track was not enabled for this run" is a report. An empty endpoint table is not.
26.3 Measured Dimensions — Phase 1
Workflow Coverage
Percentage, with evidence basis.
State Coverage
Percentage, with evidence basis.
Transition Coverage
Percentage, with evidence basis.
Endpoint Coverage
Percentage. NOT_MEASURED where the backend track was disabled.
Error Coverage
Percentage, with evidence basis.
Reconciliation Counts
Declared, Observed, Confirmed, True Gaps, Undeclared. Counts, not percentages, because the denominator is a human declaration and changes when intent changes.
Finding Counts By Severity
Counts per Section 25.
Endpoint Metrics
Latency, request volume, error rate.
26.4 Scoring By Phase
Phase 1
No composite scores. Measured dimensions and evidence states only.
Phase 2
Workflow Health Score
0 - 100
Justified by continuous production evidence and an established baseline. A health score is a statement about change over time, which production traffic can support.
Endpoint Health Score
0 - 100
Phase 3
Release Confidence Score
0 - 100
Requires release-tagged graph versions. See BGS Section 19.1.
Quality Score
0 - 100
Composite assessment across declared intent, demonstrated behavior, production behavior and release history.
QRS-SCORE-001
A composite score shall be published only where the evidence supporting it is continuous. A score computed from a single point in time shall not be published at any phase.
QRS-SCORE-002
Every published composite score shall expose its inputs and its confidence.

27.1 Report Determinism
QRS-DET-001
Report content shall be computed deterministically from recorded evidence and shall be reproducible from that evidence.
QRS-DET-002
No report content shall be generated by a language model. Assisted intelligence operates on intent declaration, never on analytical output. See the MVP Scope Document, Section 9.1.
QRS-DET-003
Every finding shall be traceable to the evidence events that produced it.
28. Phase Evolution
Phase 1 — Behavioral QA & Intent Reporting
Reports Available:
* Executive Quality Report
* Flow Coverage Report
* Behavioral Graph Report
* Missing Flow Report
* Missing State Report
* Flow Reconciliation Report
* QA Run Report
* Instrumentation Report
* Session Analysis Report
* Endpoint Intelligence Report
* Graph Drift Report (Groundwork)
Scoring:
None. Measured dimensions and evidence states only.
Goal:
Understand what the application is supposed to do,
what it was seen doing, and the difference.


Phase 2 — Production Monitoring, Feedback & Analysis Reporting
Additional Reports:
* Workflow Health Report
* User Journey Report
* Guidance Report
* Database Intelligence Report
* Error Investigation Report
Scoring:
Workflow Health Score and Endpoint Health Score become
publishable, justified by continuous production evidence.
Goal:
Understand production behavior,
and say what to build, fix or change next.


Phase 3 — Autonomous Behavioral Intelligence Reporting
Additional Reports:
* Release Validation Report
* Regression Report
* Generated Test Report
* Failure Simulation Report
* Behavioral Anomaly Report
* Remediation Report
* Network Divergence Report
* Quality Intelligence Report
Scoring:
Release Confidence Score and composite Quality Score
become publishable, with inputs and confidence exposed.
Goal:
Understand, explain, and act on quality.

QRS-GUID-001
Guidance shall distinguish a declared flow that is unreachable in production (a defect) from one that is merely undemonstrated (a coverage gap).
QRS-GUID-002
Guidance shall be ranked by observed user impact.
QRS-GUID-003
Where evidence is insufficient to support guidance, the report shall say so rather than issue weakly supported guidance.

29. Success Criteria
The QA Reporting System shall be considered complete when engineering teams can:
1. Understand application behavior without reviewing raw telemetry.
2. Tell what was measured apart from what was not.
3. Identify workflow coverage gaps automatically.
4. Identify missing states and missing flows automatically.
5. See where observed behavior diverges from declared intent, in both directions.
6. Investigate failures using contextual reports.
7. Monitor production workflow health.
8. Receive guidance on what to build, fix or change next.
9. Validate releases using behavioral evidence.
10. Detect regressions automatically.
11. Generate test suites from observed behavior.
12. Receive explainable quality recommendations.
13. Continuously assess software quality through autonomous intelligence.
