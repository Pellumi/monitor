COMPONENT DESIGN DOCUMENT (CDD)
1. Purpose
This document defines the detailed design of all system components within the Self-Observing Testing System (TELLANN).
The purpose of this document is to:
* Define service responsibilities
* Define internal component structures
* Define service interfaces
* Define APIs
* Define event contracts
* Define storage interactions
* Define processing workflows
* Support implementation planning
* Support service-level testing
* Support future extensibility

2.1 Reading This Document
Components are grouped by layer, not by delivery order. Every component carries its phase. A component marked Phase 2 or Phase 3 is designed here so that Phase 1 does not foreclose it; it is not implemented in Phase 1.
The Assistive Layer is deliberately isolated. It is called by exactly two components — the Derivation Engine and the Document Intelligence Engine — and by nothing on the analytical path. See Section 25.1.

4.1 Desktop Agent
Service ID
CDD-AGENT-001
Purpose
Provide the controlled local environment in which an application is analyzed, instrumented and demonstrated.
Required by FR-141 through FR-165c.
Runs on
Developer machine. Not deployed to the platform cluster.
Responsibilities
* Authenticate and hold a device-bound session
* Bind, trust and snapshot a local workspace
* Analyze the codebase locally
* Plan, apply, validate and roll back instrumentation
* Drive managed browser demonstration runs
* Scope evidence by flow boundary
* Protect sensitive captured values
* Be the single egress point to the platform
Internal Modules
Desktop Agent
│
├── Main Process
│   ├── Device Identity

│
└── Renderer
    ├── Applications
    ├── Intent
    ├── Instrumentation
    ├── QA Runs
    └── Reports
Interface Model
The renderer holds no credentials and makes no network calls. It communicates with the main process through a capability-scoped bridge. Every privileged operation is a named channel with validated inputs.
Renderer
   │  (named, validated channels)
   ▼
Preload Bridge
   │
   ▼
Main Process
   │
   ▼
Cloud Client ──▶ Platform
Egress Contract
CDD-AGENT-E01
All outbound platform traffic passes through the Cloud Client, so the transmitted surface is auditable in one place.
CDD-AGENT-E02
Raw source, source archives and unreviewed working-tree diffs are not transmitted without explicit, purpose-named consent.
CDD-AGENT-E03
Run credentials and credential-store contents are never transmitted.

4.4 Instrumentation Controller
Service ID
CDD-AGENT-IC
Purpose
Apply bounded, reviewable, reversible instrumentation to a customer working tree.
Lifecycle
Detect
  ↓
Propose Plan
  ↓
Render Redacted Diff
  ↓
Human Approval
  ↓
Apply Patch Set
  ↓
Validate
  ↓
Success ──▶ Record Result
  │
  └─ Failure ──▶ Rollback ──▶ Restore Branch
Responsibilities
* Detect existing instrumentation and installed SDKs
* Resolve a plan scoped to declared flows
* Redact secrets from displayed diffs
* Apply, validate, and roll back
* Record capability actions for audit
Constraints
CDD-AGENT-IC01
No write to a customer working tree without an approved plan.
CDD-AGENT-IC02
Every applied plan has a recorded rollback.
CDD-AGENT-IC03
A validation failure attributable to the plan triggers rollback automatically.

22. Report Engine
Service ID
CDD-RPT-001
Purpose
Generate reports and exports.
Supports FR-053 through FR-059.
Report Model
Phase 1 reports are of two kinds:
Application Report
The current analytical state of an application, derived on request from the latest evidence. Addressed by application, not by report identifier.
Run Report
The report produced by a specific demonstration run. Addressed by run identifier, generated asynchronously, and retryable.
A versioned report catalogue with independently addressable report objects is specified in the API Specification, Section 24.1, and is scheduled for completion before general availability.
Responsibilities
* Coverage reports
* Missing state and missing flow reports
* Behavioral graph reports
* Session analysis reports
* Endpoint intelligence reports
* Reconciliation reports
* Run reports
* Export generation in JSON, CSV, HTML and PDF, subject to entitlement tier
Constraints
CDD-RPT-001a
Report content is computed deterministically from recorded evidence and is reproducible from that evidence.
CDD-RPT-001b
Export format availability is resolved from the organization's entitlement tier by a single shared resolver, so the report engine, the settings service and the dashboard cannot disagree about what a customer may download.
APIs
GET  /reports/{applicationId}/latest


GET  /reports/{applicationId}/export?format=


GET  /reports/{applicationId}/endpoint-intelligence


GET  /qa-runs/{runId}/report


POST /qa-runs/{runId}/report/retry

25.1 Assistive Intelligence Service
Service ID
CDD-AI-001
Phase
Phase 1 (bounded)
Purpose
Reduce the cost of stating intent.
Callers
Exactly two components may call this service:
* Derivation Engine (Tier 2 only)
* Document Intelligence Engine
No analytical engine may call it.
Internal Modules
Assistive Intelligence
│
├── Provider Interface
├── Prompt Registry
├── Input Sanitizer
├── Schema Validator
├── Output Repair
├── Invocation Log
└── Cost Aggregator
Features
* Flow generation from documents
* Flow suggestion enrichment
* Domain inference
* Structured output repair
Responsibilities
* Sanitize input before transmission
* Validate output against a schema before returning it
* Repair malformed output, or fail closed
* Log every invocation with feature, status, attribution and cost
* Aggregate usage for administrative visibility
Constraints
CDD-AI-001a
Output is always a proposal. It never enters a graph, ruleset or report without explicit human acceptance.
CDD-AI-001b
The deterministic path is consulted first. This service is a fallback, not a default.
CDD-AI-001c
Unavailability degrades assistance quality only. Every analytical component continues to operate.
Design Consequence
Because no analytical component depends on this service, the platform can be operated with the provider disabled. That property is tested, not assumed. See the MVP Scope Document, Section 9.1.

27. Design Invariants
CDD-INV-001
The analytical path — Session, Behavioral Graph, Coverage, Missing State, Endpoint, Reconciliation, Report — contains no call to the Assistive Layer.
CDD-INV-002
The Cloud Client is the desktop agent's only egress point.
CDD-INV-003
No component writes to a customer working tree except the Instrumentation Controller, and only under an approved plan.
CDD-INV-004
Every Phase 2 and Phase 3 component listed here is designed so that Phase 1 does not foreclose it, and implemented in no earlier phase than its label.
