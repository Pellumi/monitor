SYSTEM ARCHITECTURE DOCUMENT (SAD)
1. Introduction
1.1 Purpose
This System Architecture Document defines the architecture of the Self-Observing Testing System (TELLANN).
The document describes:
* Architectural principles
* System structure
* Major subsystems
* Component interactions
* Data flow
* Storage architecture
* Deployment architecture
* Security architecture
* Scalability architecture
* Evolution roadmap across all product phases
The purpose of this document is to provide a blueprint for implementation and future system growth.
2. Architectural Vision
TELLANN is designed as a distributed behavioral intelligence platform that continuously:
Observe Applications
↓
Capture Behavioral Data
↓
Process Telemetry
↓
Construct Behavioral Models
↓
Analyze Quality
↓
Generate Insights
↓
Support Autonomous Validation
The architecture must support progressive evolution from:
Phase 1:
Behavioral QA & Intent Platform
to
Phase 2:
Production Monitoring, Feedback & Analysis
to
Phase 3:
Autonomous Behavioral Intelligence
without requiring architectural redesign.
A defining property of the architecture is that it spans two trust zones. Part of the platform runs in Tellann's cloud. Part runs on the developer's own machine, holds their source code, and modifies their working tree. Those two zones exchange evidence and instructions, never raw source, unless the developer explicitly consents.
3. Architectural Principles
AP-001 Event-Driven Architecture
All platform operations shall be driven by behavioral events.
AP-002 Cloud-Native Design
All services shall be independently deployable.
AP-003 Scalability First
Every major component shall support horizontal scaling.
AP-004 Multi-Tenant Architecture
Customer environments shall be logically isolated.
AP-005 Observability by Default
Every platform component shall generate telemetry.
AP-006 Privacy by Design
Privacy controls shall be enforced throughout the data lifecycle.
AP-007 Extensibility
New analytics modules shall be attachable without redesign.
AP-008 AI-Ready Foundation
Architectural decisions shall support future intelligence capabilities.
AP-009 Local-First Source Handling
Customer source code shall be processed on the developer's machine by default. Only derived artifacts, evidence, and explicitly consented uploads shall cross into the platform.
AP-010 Deterministic Analysis
Every analytical output the platform publishes shall be computed deterministically from recorded evidence and shall be reproducible from that evidence. Language models occupy an assistive path that is structurally separate from the analytical path.
AP-011 Reversible Intervention
Any change the platform makes to a customer system shall be planned, reviewed, recorded and reversible.

7.1 Desktop Agent Architecture
Purpose:
Provide the controlled local environment in which an application can be analyzed, instrumented and demonstrated.
The desktop agent is not an optional convenience. It is where Phase 1's core loop executes. A demonstration run cannot be started anywhere else.
Process Model
Desktop Agent
│
├── Main Process
│   ├── Authentication & Device Identity
│   ├── Secure Credential Store
│   ├── Workspace Manager
│   ├── Git Checkpoint & Branch Policy
│   ├── Codebase Analysis Worker
│   ├── Document Processor
│   ├── Instrumentation Controller
│   ├── Run Orchestrator
│   ├── Browser Observer
│   ├── Local Relay
│   ├── Cloud Client
│   ├── Notification Client
│   └── Update Manager
│
├── Preload Bridge
│   └── Capability-scoped IPC surface
│
└── Renderer
    ├── Applications
    ├── Intent
    ├── Instrumentation
    ├── QA Runs
    └── Reports
Component Responsibilities
Authentication & Device Identity
Authenticates through the system browser. Holds a device-bound session. A session is valid for one machine and is revocable per device.
Secure Credential Store
Holds platform tokens and run credentials using operating-system protected storage. Run credentials are never persisted to platform storage.
Workspace Manager
Binds a local repository to an application, records trust status, takes repository snapshots, and supports cloning into a new workspace.
Git Checkpoint & Branch Policy
Records the developer's branch state before intervention, enforces configured branch policy, issues time-boxed checkout grants, and restores the original branch afterwards.
Codebase Analysis Worker
Builds a code graph from the bound workspace in staged, cancellable runs. Produces analysis projections, warnings and evidence references. Source is read locally; only projections leave the machine.
Document Processor
Imports customer product documents, versions them, and prepares them for intent drafting.
Instrumentation Controller
Detects existing instrumentation, resolves a plan against declared flows, renders redacted diffs for review, applies an approved patch set to the working tree, runs validation commands, and performs rollback.
Run Orchestrator
Manages the run lifecycle from ARMED through to COMPLETED or COMPLETED_INCOMPLETE, including pause, resume, boundary detection and evidence batching.
Browser Observer
Drives the managed browser session, captures interaction and network evidence, sanitizes URLs and payload keys, classifies protected values, and records browser findings.
Local Relay
Correlates backend SDK telemetry emitted by the locally running application with the active run session.
Cloud Client
The single egress point to the platform. Every outbound call passes through it, which makes the transmitted surface auditable in one place.
Update Manager
Manages agent version checks and update application under policy.
Transmitted / Not Transmitted
Transmitted:
* Evidence events and run lifecycle state
* Code graph projections and analysis warnings
* Instrumentation plans, capabilities and results
* Declared flow and suggestion data
* Document-derived intent drafts
* Findings, annotations and artifacts
Not transmitted without explicit consent:
* Raw source files
* Source archives
* Working tree diffs beyond the reviewed plan
Never transmitted:
* Run credentials
* Protected values in the clear
* Operating-system credential store contents
Failure Posture
The desktop agent degrades rather than blocks:
* No model provider — assistance is unavailable, everything else works
* No network — analysis and instrumentation continue locally, evidence queues
* Validation failure — instrumentation rolls back, the workspace is restored
* Browser closed mid-run — the run completes as COMPLETED_INCOMPLETE and reports the evidence it has

12.1 Reconciliation Engine
Purpose:
Diff the Declared Intent Graph against the Observed Behavior Graph.
Inputs
* Declared Intent Graph
* Observed Behavior Graph
* Compiled Ruleset
Outputs
* Three-way classification: Confirmed, True Gap, Undeclared
* Flow Reconciliation Report
* Drift record over time
Runs incrementally as new evidence arrives, not only at flow completion.
Specified in full by the Behavior Graph Specification, Section 22.5.
12.2 Derivation Engine
Purpose:
Propose states, transitions and branch flows a declarer likely intends but has not entered.
Lookup Order
Tier 1 — Internal Pattern Library
Curated, versioned QA patterns keyed by state category and semantic name.
Tier 1.5 — Cross-Tenant Structural Match
Anonymized, frequency-weighted graph shape index. Governed by FDRS-PRIV-001 through FDRS-PRIV-004.
Tier 2 — Assisted Enrichment
Consulted only where Tiers 1 and 1.5 return no usable result. Output is normalized into the same suggestion structure and labelled with its tier.
Every suggestion is a proposal. Nothing enters a Declared Intent Graph without explicit acceptance.

16.1 Schema Authority
The platform's relational schema is defined and versioned in the repository, and evolves continuously with implementation.
A separate prose data-model specification is not maintained. A document describing tables cannot be kept truthful at the rate the schema changes, and a schema document that has drifted is more damaging than no schema document, because it is trusted.
Authoritative sources:
Relational schema
The versioned schema definition and its migration history in the repository.
Analytics schema
The ClickHouse table definitions maintained alongside the ingestion services.
Storage responsibilities
This section.
Retention and classification
The Privacy & Data Collection Specification.
Architectural decisions about storage
Recorded as Architecture Decision Records. ADR-001 records the decision to store behavioral graphs relationally rather than in a dedicated graph database, with a dedicated graph store deferred to Phase 3.
SAD-DATA-001
Any architectural change to storage responsibility — a new store, a change of ownership between stores, or a change of retention class — shall be recorded as an ADR and reflected in Section 16. Table-level change requires no document update.

18. Security Architecture
Authentication
* One-time code and password authentication
* Multi-factor authentication
* OIDC federation
* SAML federation (Pre-Launch)
* System-browser OAuth with device-bound sessions for the desktop agent
Authorization
The platform enforces authorization through organization membership roles. Roles are coarse and auditable by design; the product personas described in the Functional Requirements Specification, Section 3, are job functions rather than access levels, and several personas typically share one role.
Membership Roles:
* OWNER — full control, including billing and organization lifecycle
* ADMIN — full operational control, excluding organization deletion
* MEMBER — declare, demonstrate, review and report
* VIEWER — read-only access to evidence and reports
Persona to role mapping:
Developer          → MEMBER or ADMIN
QA Engineer        → MEMBER or ADMIN
Product Manager    → MEMBER or VIEWER
Engineering Manager → VIEWER, MEMBER or ADMIN
Organization Admin → ADMIN or OWNER
Additional authorization surfaces:
* Per-device session authorization for the desktop agent
* Per-workspace trust status
* Per-application branch policy and time-boxed checkout grants
* Scoped programmatic access tokens
* Entitlement resolution gating feature access independently of role
Data Protection
* TLS 1.3
* AES-256 Encryption
* Operating-system protected credential storage on the desktop agent
* Secret Management
* Protected value classification with audited reveal
* Audit Logging

23. Phase-Based Architectural Evolution
Phase 1 — Behavioral QA & Intent Platform
Components Active:
* Desktop Agent (Layer 0)
* Frontend SDK
* Backend SDK
* API Gateway
* Event Collector
* Session Engine
* Session Replay
* Behavioral Graph Engine
* Coverage Engine
* Endpoint Analysis Engine
* Reconciliation Engine
* Derivation Engine
* Code Intelligence Engine
* Document Intelligence Engine
* Assistive Intelligence Layer (bounded)
* Report Engine
* Dashboard
* Platform Foundation services
Goal:
Establish what an application is supposed to do, observe what it actually does under demonstration, and report the difference.
Structural groundwork shipped in Phase 1:
* Graph versioning and drift comparison — extended to production baselines in Phase 2, to anomaly detection in Phase 3
* Cross-tenant structural pattern index — extended to network behavioral intelligence in Phase 3
* Assistive Intelligence Layer — extended to behavioral reasoning in Phase 3
* Recommendation evidence capture — extended to implementation guidance in Phase 2 and 3
Groundwork is scoped to what is useful on demonstration evidence alone. Nothing requiring production traffic is stubbed into Phase 1.
Phase 2 — Production Monitoring, Feedback & Analysis
Additional Components:
* Production Ingestion Path
* Workflow Health Monitor
* Journey Intelligence Engine
* Database Intelligence Engine
* Error Correlation Engine
* Guidance Engine
Architectural change required:
The ingestion path must separate demonstration evidence from production evidence at collection time, because they are metered differently, retained differently, and compared against one another.
Goal:
Understand the customer's system while real users are using it, and convert that understanding into guidance on what to build, fix or change next.
Phase 3 — Autonomous Behavioral Intelligence
Additional Components:
* Test Generation Engine
* Regression Engine
* Failure Simulation Engine
* Behavioral Anomaly Engine
* Network Behavioral Intelligence
* Remediation Engine
* Authority & Policy Service
* Quality Intelligence Assistant
Architectural change required:
An authority model in which a customer grants explicit, revocable, per-application permission for the platform to act, and every action remains attributable and reversible.
Goal:
Understand a running system continuously, remediate in real time under customer authority, and use network-scale behavioral intelligence to propose implementation changes.
24. Architectural Invariants
The following must remain true at every phase. They are what separates the platform from a tool that guesses.
SAD-INV-001
Analytical output is deterministic and reproducible from recorded evidence.
SAD-INV-002
Assistive intelligence proposes; it never decides, and it is never on the analytical path.
SAD-INV-003
Customer source is processed locally and leaves the machine only on explicit, purpose-named consent.
SAD-INV-004
Any change made to a customer system is planned, reviewed, recorded and reversible.
SAD-INV-005
The platform holds no authority over a customer system by default.
SAD-INV-006
Tenant isolation holds across every store, every engine and every index, including anonymized aggregate indexes.
SAD-INV-007
Removing the model provider degrades assistance quality and nothing else.
